## THE TOKEN COUNTS ARE EXACT

The counts above come from DeepSeek's own tokenizer: the published
`deepseek-ai/DeepSeek-V3` `tokenizer.json`, 128,000 vocabulary entries and
127,741 merges, implemented directly because this lane holds no DeepSeek API key.
It was validated two ways over this corpus: every produced symbol exists in the
published vocabulary with zero exceptions, and decoding the produced tokens
reproduces the original text byte for byte. The first implementation failed that
second proof and was fixed rather than reported.

For scale, against DeepSeek's published context limits: the largest piece is
73,370 tokens. That is inside the 1M context of the current `deepseek-v4-pro` and
`deepseek-flash` with more than 13x headroom, and still inside the 128K context of
the retired `deepseek-chat` and `deepseek-reasoner` models. The whole Master Spec as
ONE file is 212,785 tokens, which also fits a 1M context.

## WHY FOUR, AND WHAT A SMALLER READER WOULD NEED

The cut counts BYTES, because a fetch counts bytes. The Master Spec is 756,386 bytes,
and the largest piece here is 259,991 bytes.

A reader that accepts F bytes needs at least ceil(756,386 / F) pieces.

| reader accepts | minimum pieces | this cut gives |
| --- | --- | --- |
| 1,048,576 bytes (1 MiB) | 1 | 3 |
| 524,288 bytes (512 KiB) | 2 | 3 |
| 262,144 bytes (256 KiB) | 3 | 3 - minimal |
| 131,072 bytes (128 KiB) | 6 | 3 |

So three pieces is the fewest possible for any reader that takes a quarter of a
megabyte, and the same three also fit a 128K-token context, which one piece of
212,785 tokens would not.

If a reader truncates below 259,991 bytes, re-cut smaller: the generator takes the
target byte size as a parameter, and the losslessness proof does not change.
